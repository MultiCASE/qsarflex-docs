Estate considerations
Virtual and shared desktops

The install is per-user, and on the Local build so is the ≈4.0 GB reference data — there is no shared or machine-wide copy. On non-persistent VDI or multi-session Windows Server that cost multiplies per session or per rebuild. Put it to MultiCASE (section 13) rather than assuming it works; the Cloud build or the web application is usually the better fit for those estates.

Roaming profiles

The application and its data both live under the local profile, not the roaming one — the only thing in %APPDATA% is the web view's working state. A roaming-profile policy that syncs that folder will carry a user's compound library between machines, and its size with it.

Backup, and what happens when a user leaves

A user's compound library is held by the interface in the web view's own storage, not in a document they save. Plan for it explicitly: it is the kind of data a reviewer assumes is backed up, and it is not.

There is one copy

MultiCASE holds none — the backend evaluates and returns, it does not store libraries — and the product has no export of the library as a set. Whatever protects the user's profile is what protects the library.

Back up the profile

Include the web view store in the profile backup and the library is covered; section 06 gives its path on each platform. Exclude the ≈4 GB reference data — it costs backup space and re-downloads on demand.

Offboarding

Uninstalling does not remove it. To decommission a machine, delete the web view store as well as the application — section 06 gives its path, and sections 03 and 04 cover uninstall on Windows and macOS.

Signing out clears the library. Sign-out discards the compound library and the evaluation results on that machine, and there is no undo. Tell users to download the results they need before signing out, and treat a forced re-authentication the same way.

Reference data files

The Desktop — Local build evaluates compounds on the workstation, which means it needs MultiCASE's model and reference data on the workstation. These files are not bundled with the installer: they are downloaded on first launch and updated independently of the application.

Model files
27 MB
FilterModels.zip — the model definitions and their small reference sets.
Reference database
4.0 GB
na_master_db.sqlite — the analogue and nitrosamine reference database.
Free space needed
10 GB
To cover the download and extraction comfortably alongside the application.
Where the files are stored
Windows %LOCALAPPDATA%\QSARFlex\data\
macOS ~/Library/Application Support/QSARFlex/data/
Download behaviour
On first launch the application reads a manifest at downloads.multicase.com and downloads whatever is missing before evaluation is allowed.
On later launches it re-reads the manifest and offers an update when the published data has changed. Nothing is downloaded without the user starting it.
Every download is verified against a SHA-256 checksum — the archive as a whole, each extracted model file, and the database. A corrupted or tampered download is rejected.
The data directory is left untouched by application updates, so a version update does not re-download the ≈4.0 GB database.
If the machine is offline and the data files are present, the manifest check is skipped without an error. That is a convenience, not offline operation — see section 11.
Planning the rollout

Every Local workstation downloads its own copy — no shared network location, no peer distribution. Twenty workstations means twenty downloads of ≈4.0 GB each. An interrupted download does not resume; it restarts from the beginning, which is the practical argument for staging a rollout rather than letting a department start on the same morning. The transfer is verified before it replaces anything, so a partial download is never silently accepted — nor salvaged. It is one connection with a two-hour ceiling, so a workstation must hold roughly 5 Mbit/s for the whole download or it times out and starts again from nothing.

What sits in the data directory, and who can read it

Both are encrypted at rest as shipped — the model files with AES-256, the reference database as an encrypted SQLite database. They are MultiCASE intellectual property, not customer data, and they land in the signed-in user's profile under that user's permissions, so another user on the same machine cannot read them. Traffic runs one way: the application downloads and verifies, and has no code path that uploads anything from this directory. Nothing you evaluate is written here either.

Section 06
Web rendering runtime

Both desktop applications draw their interface with the operating system's web view, loading files from inside the installation. No page is fetched from the internet to render the interface, and no browser is embedded in the installer.

Windows — WebView2

The Windows application hosts a Microsoft Edge WebView2 control. WebView2 is a Microsoft system component, updated by Microsoft alongside Edge, and needs no action from IT once present.

Windows 11: included by default. Nothing to do.
Windows 10: present on most updated machines. Where it is missing, the Evergreen Runtime can be pre-deployed through Group Policy or your software management tool.

Microsoft publishes the Evergreen Bootstrapper at developer.microsoft.com/microsoft-edge/webview2/

macOS — WKWebView

The macOS application hosts WKWebView, part of the WebKit framework built into macOS. There is nothing to install or configure, and it is updated with macOS itself.

What the web view can and cannot do
It does
Render the application's own interface from files inside the installation
Call the application's own code for evaluation, curation and reporting
Display a generated report, and hand it to the operating system's print dialog
It does not
Act as a general-purpose browser — there is no address bar and no arbitrary navigation
Load or run browser extensions
Fetch the interface from the internet; sign-in happens in the user's own browser, not here
Web view store — Windows
%APPDATA%\QSARFlex\WebView2Main — note this is the roaming profile, not the local one.
Web view store — macOS
~/Library/WebKit/, in a folder named for the installed build — not under Application Support, which holds only reference data.
What it holds
The web view's cache and profile, and the interface's own working state — the compound library, the evaluation results and the DataKurator working set, including structures, names and registry numbers. It holds no credentials and no session tokens. It is per-user and not separately encrypted, so on a managed estate rely on full-disk encryption. What the user sees
A notice that an update is available. Work in progress is not interrupted and nothing downloads yet.
If they accept, the download runs in the background with visible progress.
The new version is applied when the application next restarts. The previous version's folder is removed once the new one is in place.
A reference-data update follows the same pattern and is verified by checksum before it replaces anything.
What an update touches
The per-user application folder, and the per-user uninstall entry's version value
Nothing in the reference-data directory — an application update never re-downloads it
No system directory, no machine-wide registry key, no shared component
If an update goes wrong

There is no in-app rollback. The recovery path is to uninstall and reinstall from the installer for the version you want, which leaves the reference data in place — so recovery on a Local workstation does not mean another ≈4.0 GB download. Raise a ticket before you do this on more than one machine.

A reference-data update can change a prediction, and the previous data is not kept. A data update replaces the files in place; there is no second copy to fall back to. If you validate results against a specific data version, record which version you validated. There is no version pinning inside the application. A workstation follows the feed for the channel it was installed from. If you need a controlled rollout — validating a version before your users receive it — the practical lever is network access to downloads.multicase.com, which you can hold closed until you are ready. Section 08
Authentication and sessions

QSAR Flex signs in with a MultiCASE Account. Passwords are never held by the application: they are entered on the MultiCASE Accounts sign-in page and validated by that service directly. The same account is used for QSAR Flex, the support portal and other MultiCASE products.

Desktop sign-in flow
1
The user chooses Sign in. The application opens the MultiCASE Accounts page at auth.multicase.com in the user's default browser — not in an embedded window.
2
The user signs in. Credentials go from the browser to the MultiCASE Accounts service over HTTPS and are never seen by the application.
3
The browser is redirected to a QSAR Flex page which hands the result back to the waiting application through the registered URL scheme, on the same machine.
4
The authorisation code is exchanged for tokens server-side by the MultiCASE backend, so no client secret is shipped inside the application. Only a short-lived identity token is returned to the desktop app.
5
The application refreshes that token about every five minutes while it runs, by asking the MultiCASE backend — it never holds a long-lived refresh token itself.

The desktop applications write no session tokens to disk. Tokens are held in memory for the life of the process. There is nothing in the Windows Credential Manager, the registry, the macOS Keychain or any file on disk to steal — and, as a consequence, the user signs in each time the application is started.

Session rules
One session per productSigning in on another device ends the session on the first. A user cannot hold two live sessions for the same product.
Sign-outSigning out invalidates the session with the MultiCASE Accounts service, not only locally.
Transient failuresA network or server error does not sign the user out; only an explicit rejection of the session does.
Web applicationThe web application uses the same accounts service and the same one-session rule. Its session lives in the browser.
IdentityAn account is identified by email address and belongs to one company. Company administrators manage their own users (see section 11).
Token lifetime
Identity tokens are short-lived — minutes, not hours — and refresh in the background while the application is open.
What the browser holds (web app)
A session cookie, plus the working set in browser local storage — the compound library, the evaluation results and the DataKurator set, including structures and names. It survives a browser restart, and only signing out clears it. Nothing goes to a server-side account record; on a shared machine treat it as you would the desktop web view store (section 06).
Password policy and reset
Handled entirely by the MultiCASE Accounts service. The application has no password store and no password logic of its own.
Federated sign-on
QSAR Flex signs in against MultiCASE Accounts. Raise SAML or OIDC federation with your own identity provider with MultiCASE before you plan the deployment.

Section 09HTTPS 443 — plus 5432 on Cloud
Network requirements

Almost all communication is HTTPS on port 443 with TLS 1.2 or later. There is one exception, and it matters: the Desktop — Cloud build also makes a direct PostgreSQL connection on TCP 5432 to query its hosted reference database. That session is not HTTPS, and the client negotiates TLS opportunistically — it does not require encryption or verify a server certificate. If your policy requires structures to travel only over verified TLS, treat this as an open item for MultiCASE (section 13). The Local build and the web application use HTTPS only. The applications open no inbound ports — there is no listening socket, service or daemon.

Section 09
Network requirements — continued
Proxies
The system proxy configuration, including a PAC script, is used for HTTPS; there is no separate proxy setting inside the application. The application supplies no proxy credentials and offers nowhere to enter them, so a proxy that requires NTLM, Kerberos or Basic authentication rejects its requests and sign-in, licence checks, updates and the reference-data download all fail. Where an authenticating proxy is enforced, exempt the hostnames in this section from proxy authentication. The Cloud build's PostgreSQL session cannot traverse an HTTP proxy — that build needs direct outbound egress to central-db.multicase.com on 5432, which is often the deciding constraint in an estate with no direct egress.
TLS inspection
Where outbound traffic is inspected, the inspection certificate must be trusted by the system trust store — the Windows certificate store, or the macOS keychain. Certificate pinning is not used.
Local IPC
The Windows application uses a named pipe and a single-instance mutex to pass the sign-in result between its own processes. Neither is a network socket.
Inbound
Nothing. No inbound firewall rule is needed on the workstation.
Where the services sit
MultiCASE Accounts, the licensing backend and the usage records it holds, the evaluation service and the hosted reference database all run in Amazon Web Services, US East (Ohio). This applies to every build: Desktop — Local sends no structures, but its sign-in and licence traffic still terminates there. Confirm current arrangements with MultiCASE if you have a data-residency requirement.

Section 10Read this one
Where chemical structures go

This is usually the question that decides the deployment. The answer differs by build — including between the two desktop builds — so all three are set out in full.

Desktop — Local
Structures stay on the workstation

Evaluation, structure drawing, report generation and curation all run in the application against the local reference data. Structures are not sent anywhere.

The only things that leave the machine
Authentication traffic between the browser, the accounts service and the backend
A licence check at start-up, and a usage record per evaluation — user and product identifiers, module identifiers, item count, version, platform
Update checks, carrying version information only
A PubChem lookup — DataKurator's, which asks first, or Add Compound's Auto Fill, which does not
Desktop — Cloud
The models are local; the reference database is not

The models run on the workstation exactly as on the Local build. What differs is the reference database: instead of a downloaded copy, the application opens a direct connection to a MultiCASE-hosted database and queries it as it works.

Some of those lookups carry the structure being evaluated — a canonical SMILES string is sent as a bound query parameter to match reference records. So on this build structures do leave the workstation, even though the modelling does not. The nitrosation lookups are the clearest case; treat any module that consults the reference database as capable of it.

Note what is not claimed here: no retention commitment is made for these queries. Section 13 gives you the question to put to MultiCASE before choosing this build.

Web application
Structures are sent for evaluation, and not retained

Structures are transmitted to the QSAR Flex service over HTTPS so it can evaluate them, generate reports, draw depictions and run DataKurator's curation checks. Results are returned to the browser. Structures are not persisted in a database after the request.

Note that this includes curation: in the web application, DataKurator's analysis and correction steps are performed by the service, not in the browser.

Two PubChem paths, and only one asks. DataKurator's verification is off by default and gated by a dialog naming what would be sent. Add Compound's Auto Fill is not gated — pressing it sends what you typed straight to PubChem, on the Local build too. Block the PubChem host if that matters; nothing else depends on it.

Section 11
Licence verification and usage reporting
How verification works
Desktop — Local and Cloud

At start-up the application asks the MultiCASE backend for the active licence and the modules it covers, and will not proceed without one. Because both desktop builds evaluate on the workstation, entitlement is then enforced locally for that session.

Web application

The evaluation service validates the licence itself, server to server, on every evaluation and every report generation. The browser is not trusted to assert its own entitlement.

What a licence request contains
User identifierAn opaque account identifier. Not a name, not an email address.
Product and modulesA fixed identifier for QSAR Flex, and which modules are being used.
Item countHow many compounds are being evaluated.
Version and platformThe application version and which build it is.
Never includedNo chemical structures. No machine or hardware identifiers. No personal data beyond the account identifier.

No build works offline — Desktop — Local included. Every launch needs sign-in and a licence check, and every evaluation needs a live entitlement check: the module picker fetches your licensed modules from user-manager-be.multicase.com, and if that call fails no module can be selected. Local data removes the download, not the dependency.

How a test is counted

One run consumes the library size multiplied by the number of distinct bundles the selected modules belong to. Three modules from one bundle cost the same as one; three bundles cost three times as much. A fixed-term subscription is not metered this way; an On Demand subscription is.

What MultiCASE retains

A usage record per evaluation — who ran it, when, how many items, which modules, and its billing state. That record is what your administrators read back as licence activity, and what an invoice is reconciled against. No chemical structures are recorded in it.

Enterprise administration

An enterprise licence carries a fixed number of seats. Your own administrators assign and remove seats, create users, grant administrator rights and activate the company's licence — from inside the product, without involving MultiCASE.

No service, scheduled task or kernel driver is installed.

Verifying the signature yourself
Windows signtool verify /pa /v QSARFlex-Local-Installer.exe

Expect a valid chain and a timestamp. Get-AuthenticodeSignature reports the same without the Windows SDK.

macOS codesign -dv --verbose=4 "/Applications/QSAR Flex.app" spctl -a -vv "/Applications/QSAR Flex.app"

Expect a Developer ID authority and source=Notarized Developer ID from spctl.

Prefer a publisher rule to a path rule. The executable lives under QSARFlex-Local\current\, and Velopack repoints current at each new version, so a rule pinned to one version breaks at the next update. An AppLocker or WDAC publisher rule for MultiCASE Inc. survives updates; on macOS a Team ID rule does the same.
