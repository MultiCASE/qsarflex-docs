Estate considerations

Virtual and shared desktops. The install is per-user and so is the ≈4.0 GB reference data; there is no shared or machine-wide copy. On non-persistent VDI or multi-session Windows Server that cost multiplies per session or per rebuild. Put it to MultiCASE (section 8) rather than assuming it works; the web application is usually the better fit for those estates.

Roaming profiles. The application and its data live under the local profile; the only thing in %APPDATA% is the web view's working state. A roaming-profile policy that syncs that folder will carry a user's compound library between machines, and its size with it.

The URL scheme is used for one thing only: handing the sign-in result back from the browser to the application on the same machine. At first launch the application offers to download its reference data and the user starts it (section 3).

Reference data, web runtime and updates
Section3
Reference data

At first launch the desktop application downloads its model files and reference database, ≈4.0 GB, into the signed-in user's profile. Allow at least 10 GB free. Every workstation downloads its own copy; there is no shared location and no peer distribution.

%LOCALAPPDATA%\QSARFlex\data\ Windows ~/Library/Application Support/QSARFlex/data/ macOS

Encrypted at rest as shipped (model files with AES-256, the database as encrypted SQLite) under the user's own permissions. MultiCASE intellectual property, not customer data; the application only downloads and verifies. Nothing you evaluate is written here.

Stage the rollout. The transfer is one connection with a two-hour ceiling, so a workstation must hold roughly 5 Mbit/s throughout or it times out and starts again from nothing. An interrupted download does not resume.

Web rendering runtime

The desktop application draws its interface with the operating system's web view, from files inside the installation; nothing is fetched from the internet to render it. It is not a general-purpose browser: no address bar, no arbitrary navigation, no extensions.

WindowsMicrosoft Edge WebView2, updated by Microsoft alongside Edge. Included in Windows 11 and present on most updated Windows 10 machines; where missing, pre-deploy the Evergreen Runtime through Group Policy or your management tool.
macOSWKWebView, part of the WebKit framework built into macOS. Nothing to install or configure; updated with macOS itself.
Web view store%APPDATA%\QSARFlex\WebView2Main, the roaming profile, and ~/Library/WebKit/, in a folder named for the build and not under Application Support. It holds the cache, the profile and the user's working set including structures; no credentials, no session tokens, and not separately encrypted, so rely on full-disk encryption. Section 6 covers backup and offboarding.
Software updates
Source and frequencydownloads.multicase.com. Checked at launch and every 15 minutes while running, for application and reference data both.
User controlThe user is notified and must start the download. Nothing downloads without user action, and no administrator rights are required.
Applying an updateThe application restarts itself as soon as the download finishes, not at the next launch; the remembered sign-in carries across the restart. Reference-data updates work the same way and are checksum-verified first.
Blocking updatesDenying outbound access to downloads.multicase.com blocks application and reference-data updates, and on a first install prevents the reference data arriving at all.

Authentication, licensing and usage
Section4

Passwords are entered on the MultiCASE Accounts page in the user's own browser and validated there; the application never sees or stores one. The same account serves QSAR Flex and the support portal.

Neither deployment works offline, the desktop included. Every launch needs a session and a licence check, and every evaluation needs a live entitlement check against user-manager-be.multicase.com; if that call fails, no module can be selected. Holding the reference data locally removes the download, not the dependency.

Desktop sign-inOpens auth.multicase.com in the default browser, not an embedded window. The authorisation code is exchanged for tokens server-side, so no client secret ships in the application, and the result returns through the registered URL scheme.
Tokens at restOne identity token, in the macOS login Keychain or a DPAPI-protected file in the user's Windows profile, readable by that user on that machine only. No refresh token, password or secret. At launch the app refreshes it; if the session is no longer honoured, the browser sign-in runs again.
SessionsOne live session per product: signing in on another device ends the first. Signing out invalidates the session at the accounts service, not just locally. A network or server error does not sign the user out; only an explicit rejection does.
Identity and federationAn account is an email address belonging to one company; company administrators manage their own users. Password policy and reset sit entirely with MultiCASE Accounts. Raise SAML or OIDC federation with MultiCASE before planning the deployment.
What the browser holdsWeb application only: a session cookie plus the working set in browser local storage: the workspace, its results and its curation state, structures included. It survives a browser restart; only signing out clears it. Nothing goes to a server-side account record.
Licence verification

On the desktop the application asks the backend at start-up for the active licence and will not proceed without one; the module picker then re-checks entitlement live before every run. In the web application the evaluation service validates the licence server to server on every run; the browser is never trusted to assert its own entitlement.

A licence request carriesAn opaque account identifier, not a name or an email address; a fixed product identifier, which modules are in use, how many compounds are being evaluated, and the application version and platform.
Never includedNo chemical structures. No machine or hardware identifiers. No personal data beyond the account identifier.
How a test is countedOne run consumes the library size multiplied by the number of distinct bundles the selected modules belong to, so three modules from one bundle cost the same as one. A fixed-term subscription is not metered this way; an On Demand subscription is.
What MultiCASE retainsA usage record per evaluation: who ran it, when, how many items, which modules, and its billing state. That is what administrators read back as licence activity and what an invoice reconciles against. No chemical structures are recorded in it.
Enterprise administrationAn enterprise licence carries a fixed number of seats. Your own administrators assign and remove seats, create users, grant administrator rights and activate the licence, from inside the product, without involving MultiCASE.

HTTPS on 443, outbound only
Network requirements
Section5

Every connection is HTTPS on port 443 with TLS 1.2 or later. There is no second protocol and no non-standard port to open. The applications open no inbound ports: there is no listening socket, service or daemon.

Every rule below is outbound on 443. Allow only what the deployment you are rolling out needs.

Inbound: nothing. No inbound rule is needed on the workstation. The Windows build passes the sign-in result between its own processes over a named pipe, not a network socket.

Proxies. The system proxy configuration, including a PAC script, is used for HTTPS; there is no separate proxy setting inside the application. The application supplies no proxy credentials and offers nowhere to enter them, so a proxy that requires NTLM, Kerberos or Basic authentication rejects its requests and sign-in, licence checks, updates and the reference-data download all fail. Where an authenticating proxy is enforced, exempt the hostnames in this section from proxy authentication.

TLS inspection. Where outbound traffic is inspected, the inspection certificate must be trusted by the system trust store: the Windows certificate store, or the macOS keychain. Certificate pinning is not used.

Where the services sit. MultiCASE Accounts, the licensing backend with its usage records, and the evaluation service all run in Amazon Web Services, US East (Ohio), for both deployments. The desktop sends no structures, but its sign-in and licence traffic still terminates there. Confirm current arrangements if you have a data-residency requirement.

Choosing a deployment: where structures go
Section6

Two deployments, and this is the question that decides between them.

Diazepam. On the desktop, a structure like this one is read, checked, drawn and evaluated on the workstation, and is never sent. On the web, it travels to the evaluation service and is not kept.

Desktop: structures stay on the workstation

Evaluation, structure drawing, report generation and curation all run in the application against the local reference data. Structures are not sent anywhere. The only things that leave the machine are:

  • Authentication traffic between the browser, the accounts service and the backend.
  • A licence check at start-up and a usage record per evaluation: account and product identifiers, modules, item count, version, platform.
  • Update checks, carrying version information only.
  • A PubChem lookup, either from One Step Cure, which asks first, or Enter a compound's Auto Fill, which does not.
Web application: structures are sent for evaluation, and not retained

Structures are transmitted to the QSAR Flex service over HTTPS so it can evaluate them, generate reports, draw depictions, host the ChemiGraphy editor's session and run the curation checks: the analysis and correction steps run on the service, not in the browser. Structures are not persisted after the request.

Backup, and what happens when a user leaves. The compound library lives in the web view's storage, not a document the user saves, and there is exactly one copy: MultiCASE holds none and there is no export. Back up that store (section 3); exclude the ≈4 GB reference data, which re-downloads. Uninstalling does not remove it, so delete it when decommissioning a machine. Signing out clears the library and the results, with no undo.

Code signing, firewall and antivirus
Section7
Windows
  • The application and the installer are signed with Azure Trusted Signing: SHA-256 digest, RFC 3161 timestamp, published as MultiCASE Inc. They should not trigger reputation warnings on a standard configuration.
  • The application writes only within the user's profile. Nothing is written to Program Files, to system directories, or to HKLM.
  • No service, scheduled task or kernel driver is installed.
  • No inbound port is opened. All outbound traffic goes to the hostnames in section 5, HTTPS on 443.
macOS
  • The application and the disk image are signed with an Apple Developer ID certificate and notarised and stapled by Apple, so Gatekeeper admits them without any user override.
  • The application writes only to user-owned directories. Nothing requires administrator rights after installation.
  • No kernel extension, launch daemon or background agent is installed.
  • No inbound port is opened. All outbound traffic goes to the hostnames in section 5, HTTPS on 443.
Paths to allow, where application control is enforced
Windows%LOCALAPPDATA%\QSARFlex-Local\ application binaries: current\, packages\ and Update.exe %LOCALAPPDATA%\QSARFlex\data\ reference data %APPDATA%\QSARFlex\WebView2Main\ web view profile and working state
macOS/Applications/QSAR Flex.app or ~/Applications/QSAR Flex.app ~/Library/Application Support/QSARFlex/ reference data ~/Library/WebKit/<build>/ web view store and working state
Verifying the signature yourself
Windows signtool verify /pa /v QSARFlex-Local-Installer.exe

Expect a valid chain and a timestamp. Get-AuthenticodeSignature reports the same without the Windows SDK.

macOS codesign -dv --verbose=4 "/Applications/QSAR Flex.app" spctl -a -vv "/Applications/QSAR Flex.app"

Expect a Developer ID authority and source=Notarized Developer ID from spctl.

Prefer a publisher rule to a path rule. The executable lives under QSARFlex-Local\current\, and Velopack repoints current at each new version, so a rule pinned to one version breaks at the next update. An AppLocker or WDAC publisher rule for MultiCASE Inc. survives updates; on macOS a Team ID rule does the same.

Before you approve a rollout
Section8
Decide, then allow
  • Which deployment: desktop or web (section 6). A data-governance decision; everything else follows from it.
  • Outbound HTTPS 443 to the hosts it uses (section 5).
  • Your TLS-inspection certificate trusted by the system store, if you inspect.
  • A publisher rule for MultiCASE Inc., if you enforce application control.
Provide, and tell your users
  • Windows 10 or 11 64-bit with WebView2, or macOS 12 or later on Apple Silicon; a writable user profile and at least 10 GB free per desktop workstation.
  • Sign-in is kept between launches on the machine (Keychain on macOS, DPAPI on Windows); signing in elsewhere ends the first session and that machine signs in again.
  • A PubChem lookup sends structures outside the company: One Step Cure asks first, Auto Fill does not.
  • A usage record (user, time, modules, item count) is held by MultiCASE for licensing.
Questions this guide cannot settle

The answers depend on your contract, or are commitments rather than technical facts. Put them to MultiCASE before you scale.

  • Can MultiCASE Accounts federate to our identity provider by SAML 2.0 or OIDC, and can MFA be enforced?
  • What does the evaluation service log about a request, how long is it kept, and are structures ever written to disk, a queue or a backup?
  • Are structures ever used to improve models or reference data?
  • Is there a data-processing agreement, and a current penetration test or SOC 2 report?
  • The application bundles its own .NET runtime, so OS patching does not cover it. What is the target time to ship a fix for a critical CVE, and how are we notified?
  • Are there switches for an unattended install, and what detection rule should Intune or SCCM use?
  • Is the desktop supported on non-persistent VDI or multi-session Windows Server?
  • Can a reference-data version be pinned or rolled back, and can a data update change a prediction?
